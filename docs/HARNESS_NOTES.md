# Harness notes

## Running agents: configuration failures that look like capability failures

Before reading a failed run as "the model can't do it", check that the model actually got
to act. Three harness effects produced runs that scored 0 for reasons that had nothing to do
with the puzzle. Each is fixed or excluded. `scripts/harness_audit.py` scans every run
(Harbor/OpenCode trials and both Rat Trap harnesses) for this class of failure; its table is
`runs/harness-audit.md`.

**1. Gemini 4 Carbon: OpenCode's output-token cap.**
* *Symptom.* On the Rat Trap, at OpenCode's default thinking level, the turn after the first `get_state` ended with
  31,997 reasoning tokens, 3 output tokens and finish reason `length`. There was no tool call, so no actions. This was
  the same in all 3 runs, each turn taking 272–354 s (`runs/rattrap-agents/aborted/…-20261114-2117*`).
* *Cause: the cap, not the model.* OpenCode 1.19.5 caps every turn at
  min(`limit.output`, `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX`), and the variable defaults to **32,000**. Gemini 4
  Carbon's opening plan on the Rat Trap needs **50,324 reasoning tokens**, measured with the cap raised. So at 32,000
  the plan was cut off before the model could act. OpenCode cannot re-prompt after a truncated turn.
* *The real ceiling is 65,536 tokens per turn, and both limits a reader can see are wrong, in opposite directions.*
  Neither error can be discovered without measuring.
  * **Configuring more than 65,536 looks as if it worked.** The endpoint accepts requests of 98,304 and 131,072 without
    error, then silently truncates the turn at 65,536. A turn asked for 131,072 stopped at exactly 65,536 tokens: 63,101
    output plus 2,435 reasoning.
  * **Google's published limit is lower than what applies.** Gemini's `models.get` gives this model an
    `outputTokenLimit` of 32,768, and models.dev lists the same as `limit.output`. Step 2 of the probe below used
    50,350 tokens.
  * **Headroom:** the largest turn observed, the opening plan, was **50,350 tokens against the 65,536 ceiling**. That is
    77 % of it, leaving 15,186 tokens. A harder opening plan, on a future variant, could overrun the ceiling just as
    this one overran 32,000. No setting can prevent that, but `scripts/harness_audit.py` flags such a turn.
* *Fix.* Raise the cap to **65,536**, the ceiling.
  * Two settings are needed. The variable alone is not enough, because OpenCode sends the minimum of the two values,
    and models.dev lists this model's `limit.output` as 32,768.
  * OpenCode rejects a `limit` without `context`, and `context` also sets when OpenCode compacts the history. It is
    therefore set to the model's real input window: 1,048,576 tokens, the `inputTokenLimit` from `models.get` (models.dev
    lists the same). Compaction would start at 1,028,576 tokens, which is within 2 % of the window.
  * In the Rat Trap task, `tasks/loophole-rattrap/environment/docker-compose.yaml` (generated by
    `scripts/sync_tasks.py`) sets both in the agent container:
    * `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX: "65536"`;
    * `limit.output: 65536` in `OPENCODE_CONFIG_CONTENT`, which OpenCode reads with the highest priority, over the
      `opencode.json` that Harbor writes.
  * `scripts/opencode_rattrap.py --output-token-max` does the same for local runs, with the same default.
  * The thinking level is OpenCode's default, as on Alpha.
  * `includeThoughts: true` is also needed. Without it Gemini streams nothing until it has finished thinking, and
    a turn of more than ~30k tokens outlasts OpenCode's 5-minute wait for response headers. The probe that omitted it
    lost its long turn four times: two header timeouts, a connection reset, and a fourth attempt that was stopped
    (`runs/rattrap-agents/aborted/…-20261115-133646-0`).
* *Measured, with the fix:* a 50-step probe, run in-process on macOS through OpenCode's native Google provider
  (`runs/rattrap-agents/google-gemini-4-carbon-opencode-20261115-140522-0`). It was stopped at step 50; it was not a
  scored full run.
  * **Step 2** (the turn that used to be truncated): 50,324 reasoning tokens and 26 output tokens, ending in a tool call,
    `grab(node=71)` (the mouse). It took 563.5 s.
  * **All 50 steps** ended in tool calls, with **0 empty steps**: 323 tool calls in all, including 275 actions (5.5 per
    step) and 152 moves, 25 of them blocked. No checkpoint was reached and there was no violation.
  * **Latency.** 1,880 s for the 50 steps. Excluding step 2, steps averaged 26.9 s (median 26 s), and step 2 was the
    only one over 300 s. At this rate the 852-action budget takes about 155 steps, roughly 70 minutes plus any further
    long planning turns. That is well inside the 14,400 s agent timeout.
  * **Connection resets.** There were 2 ECONNRESETs in the 50 steps, 2 minutes apart. OpenCode's AI SDK classifies them
    as retryable, and OpenCode retried each within 5 s, so no step was lost. Probe 1 retried one step four times without
    giving up. We have not confirmed OpenCode's session-level retry limit.
* *The thinking pin was a workaround we have replaced.* Before this fix, the Rat Trap task pinned `thinkingLevel: "low"`.
  * At `low` Gemini acted, but it barely reasoned: about 12 reasoning tokens per turn, and 0 in most turns.
  * The runs that stalled with long streaks of empty steps were the ones with no reasoning at all. The clearest case
    is the last Harbor run at `low` (`runs/harbor-rattrap/rattrap-gemini-thinking-low/`). It emitted 0 reasoning
    tokens in all 1,695 steps, 1,654 of which were empty, took 25 actions, and timed out at 14,400 s. It is kept as the
    evidence for this fix.
  * The Gemini 4 Carbon Rat Trap runs recorded at `low` (OpenCode runs 0–2 and that Harbor run) are excluded from the
    capability findings as harness artefacts (docs/RESULTS.md) and labelled in `runs/harness-audit.md`.
* *Difficulty, from the uncapped probe only.* The figures from the capped runs measured the cap, so no ratio is derived
  from them. On the Rat Trap Gemini reasons about **2× as much per step** as on Alpha, and its opening plan is about
  **8× its largest Alpha turn**:

  | | Rat Trap probe (50 steps) | Alpha control (110 steps, the same model, OpenCode default level) |
  |---|---|---|
  | reasoning per step, mean excluding the opening plan | 1,339 | 662 (all steps) |
  | reasoning per step, median | 1,189 | 188.5 |
  | largest single turn, reasoning | 50,324 (the opening plan) | 6,322 |
  | largest single turn, reasoning + output | 50,350 | 20,190 |

  The Alpha figures are from `runs/20261115-alpha-control/`. The three reported Alpha runs are similar: per-step means
  444–783, and largest turns of 15,758–28,279 tokens. The Alpha task keeps OpenCode's defaults, its 32,000 cap included;
  no Alpha turn has reached it.

**2. Nemotron 3.5 Super VL: output truncation.**
* *Symptom.* Through the OpenAI-compatible harness (`scripts/agent_rattrap.py`), its
  reasoning overran the 8,192-token output default. Replies came back cut off with no tool
  call: round 2's first attempt had 4 such replies (5, 15, 16 and 18 of 18). After the last of
  them the harness ended the run as "stopped talking", with 10 actions taken.
* *Fix.*
  * The output cap is now 32,768 tokens, which its endpoint allows.
  * A cut-off reply is re-prompted ("reply with a tool call now"), not counted as quitting;
    the run errors out only after 10 cut-offs.
  * `finish_reason` is now logged for every turn.

**3. Unavailable models and API errors.**
* Alpha, `gemini-2.5-flash` (3 trials): "This model models/gemini-2.5-flash is no longer
  available to new users". Zero turns, so these are **not failures** and are excluded from
  the failure analysis.
* Alpha, Gemini 4 Carbon `wRU3ykj` (the one "aborted" run): API 400 "Requests ending with a
  model turn are not supported" after 34 turns, with no actions. A provider/harness error,
  **not a capability result**; worth re-running.
* In our own harness config, a `permission` block or an unknown tool name in OpenCode's
  `tools` list made OpenCode fail before the first model call ("Unexpected server error").
  The launcher now disables only tools OpenCode 1.19.5 knows.
* No run showed permission denials or unknown-tool calls by the agent.

## Rat Trap: what the agent has, against what the human reference had

The Rat Trap reference is Tibi's own solve, recorded and replayed (docs/RATTRAP_DESIGN.md). The human and the agent
did not work through the same interface, and that asymmetry is real.

* **The human** used an interactive 3D viewer (MuJoCo's, rotate and zoom at will) with continuous control: the hand
  moved every physics step (100,336 steps, 37 grab/release cycles).
* **The agent** has:
  * the full geometry in the instruction: every part's position and size, the named passages with their centres and
    axes, the cord's length and radius, the mouse and its node, the start configuration;
  * free state queries: `get_state` returns **every** cord node (143) plus the grippers and the mouse, at no action
    cost. Runs before commit e7a7df3 saw every 6th node; that reduction is gone;
  * discrete, capped moves (≤ 30 mm per call, halting when blocked). The reference shows these suffice: converted to
    them, the human solve takes 284 actions, a third of the budget;
  * a route-independent success test: the frozen cord slides free in a straight line. The partial credit follows the
    reference route's checkpoints, but a solve is a solve by any route.
* **Images: OpenCode does not forward MCP images to Gemini.**
  * This is a harness limitation, not a design choice. On Alpha, Gemini agents worked around it by fetching PNGs over
    raw HTTP.
  * The Rat Trap MCP tools are text only, so every model gets the same information.
  * In our own function-calling harness, Nemotron (a vision model) also received rendered images; it did no better.

## Task and puzzle

The submission tasks are `tasks/loophole-alpha`, **Alpha 1.0** (two identical interlocked
alpha tubes), and `tasks/loophole-rattrap`, **the Rat Trap** (a closed string loop with a
mouse bead, on a frame of posts, dowels, a ring and a sphere: docs/RATTRAP_DESIGN.md).
Other Alpha variants are not built as tasks or evaluated; legacy code for them is kept but
unused.

## The oracle runs in our simulator, not only in the authors' planner

The published path was checked in **our** pipeline:
1. FCL on the raw meshes: 0/214 states in collision, and 0/66,679 interpolated states at
   0.8 mm.
2. Our MuJoCo collision model: 0/28,189 dense states of the 22-pose path; MuJoCo vs FCL
   distances agree to 5.8 µm on the 214 states.
3. A **Harbor oracle run**: `solution/solve.sh` replays the 79 rig commands through the
   MCP tools (`grab`/`move`) into the simulator sidecar, with the per-substep penetration
   audit active. The separate verifier then replays the logged actions in a fresh
   simulator and recomputes the score.

Result (old distance goal, min distance > 0.4 m): reward 0.8005, 79 actions, 0 violations,
log consistent, sidecar agrees. Under the current goal (free escape by translation,
`goal.criterion: escape`) the same commands free tube B after **59 actions: score 0.851**
(local replay; the trajectory header records `expected_score` 0.851, `distance_goal_score`
0.8005).

## What is withheld from the agent: a solution oracle, not task state

The agent gets everything needed to reason about the task:
* cameras: rgb, metric depth, segmentation and the full camera model, from any viewpoint;
* tube B's pose relative to tube A, and its own handle;
* contact points, normals, penetration and forces;
* the outcome of every action (executed motion, `blocked`, `clamped`);
* the action budget and the rig limits.

What it does not get is any **solution signal**: the roadmap cost-to-go, the derived progress
value, the goal test or escape direction. These stay verifier-side. Exposing them turns the
task into black-box descent on our own planner's value function: on the original interface,
one run (`Kt5DJ3h`) did exactly that by finite differences and failed (docs/ANOMALY.md).

**Proximity (minimum distance between the tubes) is deliberately excluded**, in any form,
including a proximity value in `get_contacts`. It is a hand-made shaping signal rather than
something a robot senses. The old goal was defined through it (min distance > 0.4 m), and the
puzzle's real obstruction is topological and geometric, not metric. Contact feedback (actual
touch) is provided.

## Observation profiles and images

The task's MCP tools come from `observation.profile` in the sim config
(`loophole/configs/alpha_training.yaml` → `sensors`, `alpha_planner.yaml` → `planner`):
* `sensors` (task `loophole-alpha`): `render` (rgb / depth / segmentation + camera model),
  `get_state` (proprioception), `get_contacts` (touch). No goal, distance or progress
  values are exposed (`test_sensors_profile_hides_privileged_information`).
* `planner` (task `loophole-alpha-planner`): adds `check_motion`, `check_poses`,
  `get_geometry`. These queries change nothing and cost nothing
  (`test_check_motion_agrees_with_move`).

**Do images reach the model? Not with OpenCode + `gemini/gemini-4-carbon`.** OpenCode stores
an MCP `ImageContent` result as a tool-part attachment (a data URL) in its session, but it
does not forward it to this model. The solving agent of the 2026-11-14 eval (trial
`5oFTZb8`) said so in its final message: "Direct image attachments from `render` could not be
displayed directly because this model configuration does not accept image inputs". Most
likely OpenCode's model registry has no image-input capability for this model id; not
verified in OpenCode's source.

The agents worked around it. They called the MCP server over raw HTTP from Python, decoded
the PNGs with a hand-written decoder, and did vision in code. The solving agent:
1. rendered 50+ calibrated views;
2. reconstructed both tubes by space carving in C++;
3. planned a path with its own sampling planner on the reconstruction's distance field;
4. verified and smoothed the path offline;
5. executed it: 63 moves, never blocked, free after 64 actions.

This is why the redesigned `render` returns pixel-exact numeric channels (metric depth,
segmentation, full camera model) and the agent image ships numpy/scipy/Pillow/OpenCV: vision
works through code even when the harness does not pass images to the model. A model/harness
pair that does accept images gets the same PNGs directly.

## Reproducibility

* **Pinned:** both base images by digest (`python:3.11-slim-bookworm@sha256:a83ba18a…`);
  direct Python dependencies in `pyproject.toml`; transitive ones in
  `docker/constraints.txt` (frozen from the sim image); the agent image's compute stack
  (numpy 2.4.6, scipy 1.17.1, Pillow 13.0.0, OpenCV 5.0.0.93, mcp 1.30.0); the geometry by
  commit + sha256; OpenCode 1.19.5 via Harbor 0.25.0. Apt packages follow Debian bookworm
  and are not pinned.
* **Seeds:** the episode seed is `LOOPHOLE_SEED=0` (task.toml + compose); the roadmap was
  built with seed 1 (stored in the `.npz`); the escape directions are a deterministic
  Fibonacci lattice. Two fresh simulators given the same actions reach bit-identical
  states (`test_replay_is_deterministic`), which is what the verifier's per-action
  state-hash check relies on.
* **One episode per session:** the MCP server runs exactly one episode per process. After
  it ends (solved, budget, violation, or `/admin/finalize`), every action tool is refused
  for every client, including new MCP sessions. There is no reset tool and no reset route
  (`test_no_second_episode_without_admin_reset`).

## Network

* **Docker build needs network access:** `docker/sim.Dockerfile` downloads the Alpha 1.0
  meshes, `.cfg` and solution (pinned commit, sha256) and pip packages.
* **Agent runs have no internet.** `[agent] network_mode = "allowlist"` with
  `allowed_hosts = ["loophole-sim"]`; Harbor additionally auto-allowlists the agent's own
  model endpoint. Agent installation (`agent.setup()`) still uses the public baseline.
* The simulator sidecar declares `networks: [default]`. That keeps it out of Harbor's
  egress-control namespace, so it keeps its own DNS name and network namespace, and its
  loopback-only `/admin/*` routes are unreachable from the agent container. Without this,
  Harbor would place it in the agent's network namespace (`loophole-sim` would not
  resolve, and the admin route would become reachable over shared loopback).
* The verifier runs in a separate container with `network_mode = "no-network"`.

## Model access

OpenCode with Gemini reads only `GOOGLE_GENERATIVE_AI_API_KEY`. Harbor forwards the first
of `GOOGLE_API_KEY` / `GEMINI_API_KEY` / `GOOGLE_GENERATIVE_AI_API_KEY` it finds, so set
only that one. Models: `gemini/<id>` (e.g. `gemini/gemini-4-carbon`).

## Baselines

* **noop**: Harbor's built-in `nop` agent (`harbor run -p ./tasks/loophole-alpha -a nop`):
  no actions; score 0.
* **stop-early**: a scripted agent. The oracle harness runs `solution/solve.sh` with
  `LOOPHOLE_SOLUTION=stop_early`, which replays `solution/stop_early.jsonl` over MCP: `grab`
  plus 5 seeded random valid moves (each within the rig caps), then stops
  (`harbor run -p ./tasks/loophole-alpha -a oracle --ae LOOPHOLE_SOLUTION=stop_early`).
  Score 0: it never holds a lower cost-to-go for 3 consecutive actions.
